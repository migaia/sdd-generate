# 2 Admit — WHAT and WHY

- Write the outcome without technology: who needs what, and why. HOW belongs to Design.
- Each **Entry** is a user story with a priority (`"priority": "P1"`, `"P2"`, …). P1 is the smallest slice that delivers value alone. Give every Entry at least one acceptance that proves it independently — an Entry that can only be observed together with another is not independent, so merge the two. The highest-priority Entries become the handoff's `mvp`.
- Success criteria are measurable and technology-agnostic ("a user completes checkout in under 3 minutes", not "the API answers in 200 ms"). Record each as an acceptance case under the Entry it proves. There is no separate ID type.
- List the edge cases and failure paths the supported scope can reach. Each one either becomes a requirement or is named as out of scope.
- **Deepen, not enlarge.** When creating an SDD, adding a requirement of any size or refactoring, assume the user wants a deeper version of what they asked for, not a bigger one. Before clarifying, write down:
  - what the domain's best experts or leading products would do here that the user did not ask for;
  - the raw material they would start from (live code, data, logs, traces, specifications, real user behaviour) rather than the summary the user already prepared, and read it;
  - the concrete methods and tools they would use;
  - what, besides you and the user, can show the result is right: an executable oracle, a reference implementation, a standard or conformance suite, production data, an independent reviewer.

  Fold into the requirements and acceptance what deepens the stated outcome (a missed case, a stronger oracle, an independent source of correctness), and list each such change in the report so the user can strike it. Anything that adds a new outcome, surface or scope goes into the Clarify batch as a recommended option, never silently into Must-Ship.
- **Clarify.** Mark each unresolved point in place as `[NEEDS CLARIFICATION: D1 <question>]` (or `[需澄清: D1 …]`), define `D1` in prose, and list it in `unresolved_user_decisions`. `validate` blocks a marker whose decision is not listed, and reports `AWAITING_USER` while any decision is open. Ask at most five questions in one batch. Order them by impact (scope, then security and privacy, then user experience, then technical detail), and give each question options with a recommendation. Ask early, guesses included: a question that depends on one still open goes in the same batch, phrased on the recommended answer ("if D1 is A, …"); its answer is information even if D1 later changes. Record every answer in a `## Clarifications` log (`- YYYY-MM-DD Q: … → A: …`). Then apply it to the affected clause and remove the marker and the list entry. A user ruling given later is logged the same way and rewrites every clause it changes in that revision; a pointer to it is not an application. Departing from a ruling needs the user; between rulings, decide what existing clauses or rulings decide instead of marking it open or `blocked` ([who decides](../dispatch.md)).
