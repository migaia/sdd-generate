# 6 Report — analyze, hand off, converge

- **Preflight before handoff.** A leaf with a BC, a scaling gate or a consumed export declares `preflight` items ([contract](../v2-contract.md#compact-index)) and is not valid until `bun <create-sdd-root>/scripts/preflight.ts run --sdd <SDD>` has run them against the current code and every item passed (`SDD_V2_PREFLIGHT_REQUIRED`, `_STALE`, `_FAILED`). Items cover: each BC's candidate change as a patch that passes; each preserve acceptance run as is; each scaling gate clean (`expect: "pass"`) and with a perturbation patch it must catch (`expect: "fail"`), where a scaling gate is a requirement whose first line states an observable performance outcome (keep a static algorithm or complexity-inventory rule off that line); each acceptance that relies on a consumed export; each change acceptance seen failing with `expect: "fail"`: run at base, or, when its subject does not exist at base, under a mutation patch of the change (never an existence stub; one that already passes belongs in `preserve`); each capability the design assumes of an implemented dependency (a signature, an exported entry, a schema keyword, a naming rule) as an item that calls it; each new public TypeScript fence as a strict compile of its three commonest call sites with the real peers, so its shapes are settled before review rather than as rulings; and every repository gate command (`"gate": true`), including each `test*` and `typecheck*` script of every package the leaf writes, whose writes outside `writes` fail it. Each item runs in a disposable copy, a private repository whose scaffolding commits are not project commits (no project hook is skipped), with installed dependencies and workspace package links pointing into the copy; nothing touches the repository. A structural move or config rewrite is a patch item too, run with the preserve suite. When the repository requires green gates after every step, keep red oracles in these base runs rather than in early steps.
- **Tests forbidden.** When the user forbids running tests, do not run preflight: hand off with its items declared and `SDD_V2_PREFLIGHT_REQUIRED` (report missing) as the only blocker, named pending authorization; the host runs preflight first once authorized (`host_protocol`). When the user limits preflight to some items, run only those and leave the remaining requirements as that blocker, never as runs outside the authorization or weakened items.
- **Delivered producers and consumer gates.** A consumer leaf that needs a change in an already delivered producer does not edit it in place: the producer gets a new revision (or a new leaf) that owns the change, lists the producer's own gates, custody and export baselines among its preflight items, and the consumer depends on it. A leaf that changes a package also runs, as gate items, the scaling and size gates of every consumer that retains that package, not only its own package's scripts.
- **Amendment closure.** The report is bound to the clauses, the items and `writes`: history entries (Clarifications, implementation records) and revision bumps keep it fresh, so a Clarification that supersedes a clause rewrites that clause in the same revision, and any changed clause or item makes it stale; `validate` then lists the changed clauses and the clauses that cite them. Run `preflight.ts run --affected` (re-runs the items covering them plus every gate), re-validate, and re-review those clauses when a review is recorded. Each item keeps its own run record (time, head, patch hash, full log in `<report>.logs/`), so at completion re-run only the gates (`--only <gate IDs>`): the base runs keep their start-of-leaf record, and an edited patch makes its item stale.
- The host runs every entry of the handoff's `gates`, not a fixed list, plus the repository's aggregate entry (`make ci`, `release-check`) at batch close when one exists.
- Run `validate` once. Then analyze semantically what structure cannot see:
  - duplicated requirements
  - ambiguous or unmeasurable wording
  - underspecified steps
  - conflicts with the principles
  - requirements or Entries without acceptance
  - terminology or ordering inconsistencies

  Fix what is in scope; report the rest as limits.
- In Plan Mode, output the complete proposed SDD through `validate-draft`, never a short plan instead. When the host's own plan mode asks for a plan file, that file carries the full draft `validate-draft` accepted.
- Converge: once the host has implemented, its evidence report closes the leaf; see [converge](converge.md).
